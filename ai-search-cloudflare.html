Open with the metaphor: "Imagine walking into a hardware store. You arrive with one of three questions in your head…"

Three stations, ~75s each:
  • Register (keyword) — point at the scanner + barcode: "The customer walks up knowing exactly what they want — a part number, BR-M6100. That's a Shimano brake rotor. On the Register graphic specifically — point at the elements as you talk:
  • Barcode on the box: the part number is the index key. No interpretation needed.
  • Laser pulse: the lookup is deterministic — same query, same row, every time.
  • POS terminal screen: exact-match result, structured fields (description, fitment, price). No re-ranking, no LLM, just SQL.

Layer 1 — D1 + FTS5 — 2 min.

Lead: "The register. You walk up with an exact part number. The cashier scans it. Done."

What FTS5 is: SQLite's full-text search extension. BM25 ranking — think of it as modern TF-IDF. Free with D1.

The two halves of the left column: "Finding" is HOW I match — progressive relaxation, exact → prefix → fuzzy in one round trip. "Ranking" is HOW I order the hits — BM25, which is just three intuitions:
  • Rarity (IDF): a rare token like "BR-M6100" is worth far more than a common one like "brake."
  • Frequency (TF): more mentions score higher — but with diminishing returns, so keyword-stuffing doesn't win.
  • Brevity (length norm): the same match in a short title beats one buried in a 900-word manual.
Tie it to the card on the right: those three signals are what produce the "BM25 score 8.4."

What's interesting:
  • Lives inside D1, so no separate cluster, no separate bill
  • Co-located with the worker — engine time ≈ user-perceived time
  • Progressive relaxation: exact → prefix → fuzzy. Three queries, one round trip.
  • Measured 3–11ms in production. That's not a marketing number.
Anticipated questions:
Q: "Doesn't FTS5 fall over at scale?"
A: My parts catalog is 84K rows and the broadest prefix scan returns in 11ms. I'll worry at 10M.
Q: "What about typos?"
A: FTS5 doesn't do typo tolerance — that's why Meilisearch is on the team for the parts catalog.

Hybrid Search — 3 min.

Lead: "What if your query crosses categories? 'BR-M6100 brake makes noise.' Part of that is keyword, part is semantic."

How it works:
  • Run FTS5 and Vectorize in parallel against the same query
  • Normalize each engine's scores (BM25 ranges 0–20; cosine ranges 0–1)
  • Weighted merge: typically 60% keyword + 40% semantic, tuned per query type
  • One ranked list goes to Sonnet for synthesis
The winning result strip: "BR-M6100 final 18.2" — that's the combined score after merging. Best result wins.

Why this matters: a pure keyword search misses "clicks when I pedal." A pure semantic search misses "BR-M6100." Hybrid catches both query shapes in one round trip.

PDF Pipeline — 4 min.

Lead: "I have 2,845 PDF manuals — 593,000 chunks. But the input is brutal: OEM service manuals arrive as 80MB scanned-image PDFs, no selectable text. The phone mockup on this slide shows what I ship: a 2MB mobile-ready PDF that a tech can scroll through on 4G at the bench, AND a fully indexed retrieval layer for the AI."

This is actually two parallel pipelines from one OCR pass:
  • Retrieval pipeline (for the AI): OCR → chunk → embed → D1 + Vectorize
  • Distribution pipeline (for the human): OCR text → re-inject into PDF → font/image optimize → R2
The OCR detour worth calling out: "OCR doesn't just feed my search index — I also put the extracted text back into the PDF as a hidden layer. Visually the page looks identical to the original scan. But now if a tech opens the manual in any PDF viewer, search works. Copy-paste works. Accessibility tools work. That's a separate win from the AI side."

How I get 80MB → 2MB (point at the recipe list):
  • Subset embedded fonts: OEM manuals ship with the entire font family. I strip everything except the glyphs actually used in this document.
  • Recompress images: scanned pages are usually 600dpi PNG or uncompressed TIFF. JPEG2000 / lossy DCT at 150dpi keeps screen-readable quality at a fraction of the size.
  • Inject OCR text layer: the searchable layer adds ~50KB per manual — negligible compared to the image savings.
  • Adobe optimize to PDF/A-2u: the latest archival standard. Validates structure, strips redundant objects, normalizes color profiles.
  • Web-linearize: bytes reordered so the first page can render before the rest finishes downloading. Critical for mobile.
The mobile-ready brag: a 2MB linearized PDF means a tech in a shop on bad cellular can open it in under 2 seconds. The competitor experience (download an 80MB OEM PDF on 4G) is 90+ seconds and frequently times out.

Anticipated questions:
Q: "Why not just use ChatGPT and let it read the PDF?"
A: Two reasons. (1) Cost and latency — re-uploading 5MB on every query is wasteful. (2) The text-layer reinsertion is a separate product win — the human-readable optimized PDF only happens if I OCR myself.
Q: "Why Adobe and not Ghostscript / qpdf?"
A: Adobe's pipeline is closer to producing PDF/A-2u in one pass; open-source tooling needs more orchestration to hit the same standard reliably.
Q: "What's PDF/A-2u?"
A: ISO 19005-2 — long-term archival format. Embeds all fonts, normalizes structure, ensures the file renders the same in 10 years as it does today. The "u" means Unicode-mapped — important for the text layer.
